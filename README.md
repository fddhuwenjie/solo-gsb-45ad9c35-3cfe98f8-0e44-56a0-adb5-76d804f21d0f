# 展馆临时封路导向牌工作台

面向展馆临时封路施工的**导向牌作业工作台**。用 Python（Flask）+ SQLite + 原生 JavaScript 实现，
帮助工作人员在封闭通道前完成「登记馆区 → 拟定封路清单与换牌方案 → 逐块安装箭头牌 →
全量核对 → 正式封路」的完整流程，并在每一步自动核对「从每个入口沿实物箭头都能走到服务台」。

## 一键启动

需要本机已安装 Docker（含 Compose 插件）。在本目录执行：

```bash
docker compose up --build -d
```

启动后用浏览器打开：

**http://localhost:5000**

停止：

```bash
docker compose down          # 停止，保留数据
docker compose down -v       # 停止并删除作业数据
```

> 端口为宿主机 **5000**（映射到容器内 5000）。如被占用，可修改
> `docker-compose.yml` 中 `"5000:5000"` 左侧的宿主端口。

## 它解决什么问题

馆区里的每个路口（展厅 / 入口 / 服务台）有**实物箭头牌**，指向下一个相邻展厅。
某条双向通道要临时封闭时，被封通道上的箭头会失效，需要在相关路口**更换新箭头牌**，
保证所有入口的观众仍能沿箭头走到服务台。换牌是一块一块人工安装的，期间：

- 通道都**还没有封闭**，现场是「旧牌 + 已装新牌」混用；
- 任何一块牌装错，都可能造成断路、缺牌或循环；
- 封路清单和方案一旦开始安装就不能再改。

本系统在每次安装后立即走查全部入口，出错就**整块回滚**（此次安装不生效），
只有计划中的牌全部装好且封路后导向仍成立，才允许封闭通道。

## 作业阶段与规则

页面顶部显示当前阶段，阶段机为：

```
布展登记 setup → 拟定方案 planning → 逐块安装 installing → 已封路 closed
                                                   ↘ 封路失败 failed
```

1. **布展登记**
   - 登记展厅、入口、服务台三类路口；登记路口之间的**双向通道**（无向，一条即可）。
   - 登记各路口原有的**实物箭头牌**（每块牌固定在一个路口、指向一个**相邻**路口，
     每个路口至多一块生效箭头；服务台是终点，不设牌）。
   - 系统持续核对：**初始状态下从每个入口沿箭头都必须能走到服务台**。

2. **拟定方案**
   - **封路清单**：勾选准备封闭的通道。
   - **换牌方案**：列出待安装的新牌（在某路口把箭头改指向某相邻展厅）。
   - 此阶段清单与方案可随意增删；右侧「封路预演」会模拟清单通道封闭后的导向结果。
   - 点击「确认方案，开始安装」后，**封路清单与换牌方案立即锁定**，不可再改动。

3. **逐块安装**
   - 按方案逐块点击安装。每装一块，系统立即按
     **「全部通道仍开放 + 新旧混用的实物牌（同一路口新牌优先）」**，
     从每个入口逐步沿箭头核对到服务台。
   - 若出现下列任一情况，**指出首个出错路口并让这次安装整块回滚（不生效）**：
     - **断路**：箭头指向的通道不通（例如跨过了被封通道）；
     - **缺牌**：走到某个非服务台路口没有任何实物箭头；
     - **循环**：沿箭头走回到已走过的路口。
   - 页面会给出完整错误路径，换一块牌或调整安装顺序后重试即可。

4. **正式封路**
   - 仅当方案中的牌**全部装好**，且按封路清单模拟封闭后**所有入口仍能到达服务台**，
     「封闭通道」才会成功：清单中的通道标记为已封闭（图中红色虚线）。
   - 若最终核对失败，进入 **封路失败** 状态：**已安装的新牌全部保留，通道仍保持开放**，
     页面分别展示方案、实物牌（旧牌/新牌）与通道状态，作业终止，只能重置后重新规划。

任何阶段刷新页面或重启容器，状态都保存在 SQLite 数据库文件中（见下文数据持久化）。

## 页面说明

- **馆区示意图**：展厅（蓝）/ 入口（橙）/ 服务台（绿）；灰线为开放通道、红色虚线为已封闭；
  灰色小箭头为旧牌、绿色粗箭头为当前生效的新牌。
- **导向核对**：
  - 「现场」= 按实物牌与通道现状逐步走查的结果；
  - 「封路预演」= 模拟封路清单中的通道全部封闭后的结果。
  - 每个入口一行，显示实际箭头路径或首个出错路口及类型（断路/缺牌/循环）。
- **作业控制**：「重置作业」保留已登记的路口、通道与旧牌，清空封路清单、换牌方案、
  新装牌并打开全部通道，回到布展登记阶段。

可点击「**载入示例馆区**」快速体验：示例中初始导向正确，但**必须先装 `A展厅→C展厅`
再装 `B展厅→A展厅`**，顺序颠倒会在 `A展厅` 形成循环并被回滚。

## 技术说明

- 后端：`app.py`，单文件 Flask 应用；SQLite 表包括
  `node`（路口）、`corridor`（双向通道及开放/封闭状态）、`board`（实物牌，区分
  `old` 旧牌 / `new` 新牌）、`closure_plan`（封路清单）、`plan_item`（换牌方案及安装标记）、
  `job`（阶段机与失败原因）。
- 走查算法：对每个入口，按「新牌优先，否则旧牌」取当前路口的生效箭头，沿未封闭通道
  单步推进；遇服务台成功，遇无牌（缺牌）、目标邻边不通（断路）、重访（循环）即失败，
  并按入口登记顺序记录**首个出错路口**。安装核对时不封闭任何通道，封路核对时把清单
  通道临时视为断路，均不修改通道真实状态。
- 前端：`templates/index.html` + `static/app.js` + `static/style.css`，
  原生 JavaScript，SVG 手绘馆区示意图，无任何前端框架或构建步骤。

## 数据持久化

数据库位于容器内 `/data/signboard.db`，通过命名卷 `signboard-data` 挂载，
容器重启、刷新页面均不丢失；镜像重新构建（`up --build`）也不影响该卷。
需要彻底清空时执行 `docker compose down -v`，或在页面上「重置作业」。

## 本地不使用 Docker 运行（可选）

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python3 app.py
# 打开 http://localhost:5000 ；数据库默认 /data/signboard.db，
# 可用环境变量 SIGNBOARD_DB 指定其他路径
```
